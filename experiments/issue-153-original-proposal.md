## 背景

目前 `/jitsi` 的逐字稿流程是「有人按下紫色麥克風，才錄**他自己**的麥克風」：

- `src/views/JitsiView.vue`：每 `maxRecordingTime`（30 秒）固定切一段，上傳到 `/api/transcription/:lang`，Workers AI 的 `whisper-large-v3-turbo` 轉成文字。
- 講者名稱直接用登入帳號的名字，也就是「誰按的就是誰」。
- `meeting_sessions.recording_speaker` 只有一個欄位，設計上同時只有一位記錄者。

這個設計有三個限制：

1. **要有人記得按。** 忘了按、按晚了，前面的發言就沒有逐字稿。
2. **只錄按的那個人。** 其他與會者的發言，要靠記錄者的麥克風收到喇叭回放才會被轉錄，品質差且講者標錯。
3. **固定 30 秒切段會把句子切斷。** 句子跨段時，Whisper 兩段各自辨識，接縫處容易出錯。

另外在對照程式碼時發現兩個既有問題，不管做不做自動化都值得修：

- **時間戳是「轉錄完成」而不是「開始說話」的時間。** `sendAudioToTranscription()` 在 Whisper 回傳後才用 `timestamp: Date.now()` 建立條目。音檔在佇列裡排隊越久，時間就越不準；多人同時錄音時時間軸順序會亂。
- **兩筆條目可能互相覆蓋。** `meeting_transcript_entries` 主鍵是 `(meeting_date, ts)`，`MeetingRoom` DO 的 `save_entry` 用 `INSERT OR REPLACE`。兩人條目剛好同一毫秒時，後寫入的會無聲蓋掉前一筆。單人錄音幾乎碰不到，多人自動錄音就會。

## 提案方向：每位與會者自動錄自己（自動分軌）

這是一個**實驗性提案**，不是承諾排程。我會在自己的 fork 上慢慢試，試到哪裡就在這裡回報；如果中途卡住或實測發現方向不對，把過程記下來、讓後面的人少走冤枉路，這個 issue 就算有價值了。也歡迎大家一起討論、認領任何一段，或直接指出哪裡想錯了。

把現有的紫色麥克風流程**自動化**，加上**語音偵測切段**與**時間軸合併**。不新增伺服器，全部沿用現有的 Cloudflare 架構（Workers AI、D1、R2、`MeetingRoom` DO）。

- **入會即自動開始**：同意後自動開始錄自己的麥克風，不必再按。
- **跟 Jitsi 靜音同步**：監聽 iframe API 的 `audioMuteStatusChanged`，Jitsi 裡靜音就停、取消靜音就錄。Jitsi 的麥克風開關就是轉錄開關。
- **語音偵測（VAD）切段**：偵測到有人說話才切段上傳，不會切斷句子，也不會上傳一堆靜音。保留 30 秒作為單段硬上限。
- **講者辨識免費又準**：每段音訊本來就來自某位使用者的瀏覽器，直接標上帳號，不需要講者分離模型。
- **合併成一條時間軸**：每段帶「開始說話」的時間戳，由 DO 依時間排序合併。兩人同時說話也不會互相蓋掉。
- **紫色麥克風改成「暫停／恢復我的轉錄」**：讓使用者隨時能退出。

### 本次範圍只做錄製流程

AI 摘要、自訂範本、對逐字稿提問等功能**不在本 issue 範圍**，之後另開 issue 討論。

## 實作步驟

### 步驟 1：時間戳改成「開始說話的時間」，並避免互相覆蓋

- `JitsiView.vue`：開始錄音時記下 `startedAt`，跟著音檔一起放進 `audioQueue`；轉錄完成後用 `startedAt` 當 `timestamp`。
- `meeting-room.ts`：`save_entry` 寫入前先檢查 `ts` 是否已被占用，被占用就加 1 毫秒重試，再把實際寫入的 `ts` 廣播回去。前端仍用 `timestamp` 當 key，現有的編輯與刪除不用改。
- 新增 `migrations/0004`：`meeting_transcript_entries` 加 `speaker_uid`（帳號 ID，顯示名稱可能改名或重名）與 `source`（`auto` / `manual` / `jitsi`）。

這一步本身就是修 bug，改動小、風險低。

### 步驟 2：用語音偵測切段，取代固定 30 秒

- 新增純邏輯模組 `src/lib/vad-segmenter.ts`：輸入每一格音框的音量，輸出「開始說話」與「說完了」事件。不碰瀏覽器 API，可直接單元測試，符合「SSR 不碰瀏覽器 API」的規定。
- 初始參數（都要實測再調）：

  | 參數     | 建議值 | 作用                           |
  | -------- | ------ | ------------------------------ |
  | 音量門檻 | 依實測 | 高於此音量才算在說話           |
  | 最短語音 | 0.5 秒 | 短於此長度當雜音丟掉           |
  | 靜音延遲 | 0.8 秒 | 安靜這麼久才判定說完           |
  | 前置緩衝 | 0.3 秒 | 往前多保留，避免第一個字被切掉 |
  | 單段上限 | 30 秒  | 沿用現在的硬上限               |

- **錄音改成 AudioWorklet 錄 16 kHz 單聲道 WAV**，不沿用 `MediaRecorder`。原因：
  1. `MediaRecorder` 只能從按下那一刻錄，無法回頭補前 0.3 秒；AudioWorklet 持續寫入環形緩衝區，判定開始說話時可往前多取。
  2. `MediaRecorder` 用 `timeslice` 分段時只有第一段帶 WebM 檔頭，後面幾段不能單獨解碼；WAV 每段都能獨立轉錄。
  3. 順帶解掉 iOS 時而錄成 mp4、時而 webm 的格式問題（可能與 #137 相關）。
- 新增 `src/lib/wav-encoder.ts`。16 kHz 單聲道每秒約 32 KB，30 秒不到 1 MB。
- **要先實測**：`whisper-large-v3-turbo` 收 WAV 時辨識品質是否與 webm 相當。
- 第一階段**不引進新套件**，用音量判斷說話就夠（現有「音量測試」介面也是這樣做）。若之後要改用 Silero VAD（`@ricky0123/vad-web`），屬引進第三方套件，依 AGENTS.md 先在這裡確認。

### 步驟 3：和 Jitsi 靜音狀態同步

- 監聽 `audioMuteStatusChanged`：靜音就停止偵測並把正在錄的那段收尾；取消靜音再恢復。入會時用 `isAudioMuted()` 讀初始狀態。
- **麥克風對不上的問題**：Jitsi 在 `8x8.vc` 的 iframe 另外開了麥克風，而 `deviceId` 依網域區分，兩邊 ID 不同。要用 `getCurrentDevices()` 取得 Jitsi 用的裝置**名稱**，再比對本站的裝置清單，確保兩邊同一支麥克風。

### 步驟 4：入會即自動開始，加上同意機制

- **同意視窗**：`videoConferenceJoined` 後先跳出說明「本會議全程轉錄，你的發言會標上你的帳號名稱」，同意後才開始。同意狀態以「日期 + 帳號」存 `localStorage`。
- **不同意的人**照樣可以開會，只是發言不會被轉錄。
- **紫色麥克風改成「暫停／恢復我的轉錄」**。
- **功能旗標**：先放在旗標後面（`/jitsi?autotranscribe=1` 或管理員後台開關），旗標關閉時一切照舊，可先小範圍試用。

### 步驟 5：顯示「誰正在被轉錄」

- `meeting-room.ts`：把每條 WebSocket 連線的 attachment 擴充成 `{ userId, name, capturing }`，新增 `capture_status` 訊息，DO 收到後廣播目前名單。介面顯示「正在轉錄：A、B、C」。
- 舊的 `recording_speaker` 欄位先保留，確定沒有舊客戶端在用再移除。

### 步驟 6：上傳佇列更耐用

- 上傳或轉錄失敗最多重試 3 次，等待時間逐步拉長。
- 佇列設上限，網路斷太久時先丟最舊的段落並提醒使用者。
- 離開會議時先把未送出的音檔送完，再釋放麥克風。

### 步驟 7（第二階段，可選）：處理喇叭回音造成的重複句子

- 入會時建議戴耳機，這是最有效的做法。
- 兩位講者的段落時間重疊、文字高度相似時，標成「疑似回音」交給校對者決定。**只標記，不自動刪除**。

## 測試與驗收

- 單元測試：`vad-segmenter`（合成音量序列驗證事件時間點）、`wav-encoder`（檔頭與資料長度）、DO `ts` 衝突順延。
- i18n：新增文字三檔同步。
- 每步跑 `vp check`、`vp test`、`vp run build`、`vp run lemma:gen`，全綠才 commit。
- 實機測試沿用 #42（neo）的做法：單機、雙機、三人以上同時說話三輪，驗證時間軸順序、不互相覆蓋、靜音同步。
- 成本：每位與會者的發言都會呼叫一次 Workers AI，要先估 Workers AI 用量與費用。
